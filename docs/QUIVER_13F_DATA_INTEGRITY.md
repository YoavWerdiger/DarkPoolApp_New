## 4. אפיון הנתון — מה השורות באמת מכילות

### 4.1 100% מהשורות מגיעות מהנתיב הסינתטי

```sql
select fund_cik, filing_date, count(*) rows,
       count(*) filter (where cusip is null) null_cusip
from dark_pool_fund_holdings group by 1,2;
```

**בכל אחת מ-39 התקופות: `null_cusip == rows`.** גם `issuer_name` ריק בכל השורות.

המיפוי מ-`sec13f` אמיתי כן מעתיק את שני השדות:

```626:630:supabase/functions/sync-fund-13f/index.ts
      return {
        ticker,
        issuer_name: (h.Name ?? h.Company)?.trim() || null,
```

ו-`sec13f` אכן מחזיר אותם — ה-probe אישר את המפתחות `Date · ReportPeriod · Name · Ticker · CUSIP · Fund · Class · Value · Shares · SH/PRN · Put/Call · Direction`. לעומתו `sec13fchanges` מחזיר רק `Date · ReportPeriod · Ticker · Fund · Change · Change_Share · Change_Pct · Held · Held_Normalized · Close` — **בלי CUSIP, בלי Name, בלי Value, בלי Shares.**

**מכאן: כל שורה בטבלה נבנתה מ-`sec13fchanges`, כולל התקופה האחרונה.** הסיבה מבנית — `history.length ? history : [filing]` מעדיף תמיד את ההיסטוריה, וההיסטוריה כוללת גם את התקופה האחרונה, ולכן תוצאת `sec13f` האמיתית (155 / 705 / 2000 שורות עם `Value`, `Shares`, `CUSIP`, `Put/Call`) **נשלפת ונזרקת**.

## 5. התקלה האמיתית — מוות שקט של alias

`CURATED_FUND_QUIVER_OWNERS` ממפה `1336528 → 'Pershing Square Capital Management, L.P.'`. הישות הזו **הפסיקה לדווח אחזקות ב-2026-05-15** ומדווחת `13F-NT` בלבד מאז.

**התוצאה: הפרופיל של אקמן לא יתעדכן לעולם.** לא ברבעון הבא ולא אחריו. הסנכרון ימשיך להחזיר 155 שורות תקינות, יכתוב את אותן 16 תקופות, ויסיים ב-`ok: true`. **אין שום מנגנון שיתפוס את זה** — הבדיקה היחידה היא `rows.length > 0`, והיא עוברת.

זה בדיוק התרחיש ש-`ROSTER_WHALES_13F.md` §1.1 חזה במילים *"שינוי שם אצל המגיש (מיזוג, re-registration) שובר את הפרופיל בשקט"* — והוא **כבר קרה בפועל**, 34 ימים לפני האודיט, ולא זוהה.

הסיבה שזה חמק: Quiver מזהה לפי **string של שם**, ואנחנו מזהים לפי **CIK**. ברה-אורגניזציה השם והישות משתנים יחד, ושני הצדדים ממשיכים לעבוד — כל אחד על ישות אחרת.

### 7.2 כלל הזיהוי — לאמת מול EDGAR לפני כתיבה

לפני כתיבת שורה כלשהי עבור `(cik, report_period)`:

```
1. GET data.sec.gov/submissions/CIK{cik}.json
2. מצא רשומה עם reportDate == report_period
3. אם form == '13F-HR' או '13F-HR/A'  → כתוב. אכלס filing_date מ-filingDate
4. אם form == '13F-NT'                → 🔴 אל תכתוב. קרא את primary_doc.xml,
                                          חלץ otherManager/cik, והתריע:
                                          "FILER_REORG: {cik} → {newCik}"
5. אם אין רשומה בכלל                  → 🔴 אל תכתוב. התרע "PHANTOM_PERIOD"
6. אם SEC מראה תקופה שאין לנו          → 🟠 התרע "MISSING_PERIOD"
7. אם |our_total / sec_total − 1| > 3% → 🟠 התרע "VALUE_DRIFT"
```

הכלל הזה, אילו היה קיים, היה תופס **את כל** הממצאים כאן: את הרה-אורגניזציה (שלב 4), את התקופה החסרה של 2023-09-30 (שלב 6), ואת ×3 ואת קטיעת ARK (שלב 7). העלות זניחה — קריאת `submissions` אחת לקרן לסנכרון, ללא מפתח וללא מכסה.

בנוסף, כלל זול שאינו דורש EDGAR: **להתריע כאשר `max(report_period)` של קרן אינו מתקדם אף שחלף תאריך הגשה חוקי** (14/02, 15/05, 14/08, 14/11). זה לבדו היה תופס את אקמן ב-15/08.

### 7.3 אמון ב-Quiver ל-13F

**האמון אינו יורד — הוא עולה.** Quiver דייק בכל 39 התקופות, החזיר ערכים זהים ל-SEC עד רמת הסנט ב-6/6 השורות שנבדקו, ולא המציא דבר. שגיאה מאומתת אחת (×3 ב-2022-09-30, 1 מתוך 39 = 2.6%) בהחלט מצדיקה את בדיקת ה-VALUE_DRIFT, אך היא חריגה ולא דפוס.

המגבלה האמיתית של Quiver אינה איכות הנתון אלא **מודל הזיהוי**: `owner` הוא string חופשי, ולכן רה-אורגניזציה של מגיש שוברת את הקישור בשקט. **הפתרון שייך אצלנו** — resolution של CIK מול EDGAR, לא אצל Quiver.

לעומת זאת, **בחירת ה-endpoint שלנו כן מזיקה**: `sec13fchanges` מאבד `CUSIP`, `Name` ו-`Put/Call`. המעבר ל-`sec13f?period=` (`ROSTER_WHALES_13F.md` §5.2) נשאר העדיפות הגבוהה ביותר, ועכשיו עם הצדקה נוספת — הוא גם מייתר את `maxRows` שקטע את ARK.

### 7.4 אינטראקציה עם תוכנית `report_period` / `filing_date`

התוכנית ב-`ROSTER_WHALES_13F.md` §5.4 להפריד את `report_period` מ-`filing_date` היא **תנאי מקדים לכלל של §7.2 — ומקבלת כאן הצדקה שנייה, חזקה יותר**:

- שלב 3 בכלל הזיהוי חייב מקום לאחסן את `filingDate` האמיתי מ-EDGAR. כרגע `filing_date` מאוכלס ב-report period, ולכן **אין לאן לכתוב את התוצאה של האימות**.
- ה-`13F-NT` מוכיח ש-`report_period` לבדו אינו מזהה מספיק: לאותו `(cik, period)` יכולות להתקיים הגשות מסוגים שונים. הסכימה צריכה גם **`filing_form`** (`13F-HR` / `13F-HR/A` / `13F-NT`) ו-**`sec_accession`** — הם הופכים כל שורה לניתנת לאימות חוזר מול מסמך ספציפי.
- מומלץ להרחיב את §5.4 בשתי עמודות נוספות: **`filing_cik`** (מי הגיש בפועל) לצד `fund_cik` (הישות הלוגית שאנחנו עוקבים אחריה). זה בדיוק מה שמאפשר להציג רצף היסטורי אחיד לאקמן על פני הרה-אורגניזציה — 1336528 עד Q1 2026, 2026053 מ-Q2 2026 — בלי לשבור את ההיסטוריה ובלי לכפול פרופיל.

חסימה #3 ברשימת §5.5 צריכה לעלות בעדיפות: **היא חוסמת לא רק את המיקרוקופי אלא את כל שכבת האימות.**
